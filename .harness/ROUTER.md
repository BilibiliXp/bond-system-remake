# 文档阅读与检索路由协议

## 1. 目标

本 Harness 用来约束 Agent 以“任务驱动、最小阅读、权威优先”的方式使用项目文档，避免：

- 无目的地遍历全部文件；
- 把旧设计、当前实现和目标规则混为一谈；
- 在多个文档冲突时自行猜测；
- 修改文档后不更新索引和依赖。

## 2. 每个任务的固定流程

### 第一步：提取任务意图

从用户请求中提取：

- 任务动作：解释、检索、设计、实现、核对、更新文档或调整数据；
- 主题对象：羁绊、卡牌升级、武将/计策数据、网页 Demo、UI/资源或文档治理；
- 输出类型：结论、修改方案、代码变更、数据变更或文档变更。

不要根据单个关键词直接开始全文搜索。

### 第二步：选择路由

按 `.harness/routes.json` 的 `classification_order` 从上到下匹配。

- 通常只选择一个主路由。
- 一个任务确实跨越多个权威领域时，可以组合路由，但相同文档只读一次。
- 无法区分两个路由且不同选择会改变结论时，先向用户确认。
- 只是表达方式不同、不会改变结果时，选择范围更窄的路由继续。

开始实质工作前，应在内部记录：

```text
route: <路由 id>
goal: <本次要回答或修改的对象>
evidence: <预计使用的权威文档>
```

### 第三步：最小阅读

阅读顺序固定为：

1. 路由中的 `required`；
2. 满足触发条件的 `conditional`；
3. 为核对当前实现而读取的 `artifacts`；
4. 只有证据仍不足时，才进入受限检索。

`read` 字段含义：

- `full`：完整阅读该文档；
- `sections`：只读列出的标题及其必要上下文；
- `lookup`：只查询与当前问题匹配的记录、行或工作表。

不得仅凭文件名、摘要或搜索片段得出最终规则结论。

### 第四步：受限检索

检索按以下顺序进行：

1. 在已读文档标题中定位；
2. 使用精确名称、字段名或规则术语，在 `search_paths` 内检索；
3. 使用同义词扩展一次；
4. 仍无结果时，才扩大到项目代码或资源；
5. 是否扩大到外部资料必须由用户请求或任务必要性决定。

文本检索优先使用：

```text
rg -n "<精确术语>" <路由允许的路径>
```

禁止行为：

- 默认递归扫描 `hero_icon/`、`item_icon/`、`res/`；
- 为回答规则问题而读取无关图片；
- 在已找到权威答案后继续扩大搜索；
- 使用被路由列入 `do_not_read` 的来源。

### 第五步：形成证据链

每个规则性结论必须能对应到：

- 一个权威文档和具体标题；或
- 一个权威数据表和具体工作表/记录；或
- 一段当前代码，用来说明“现状”，而不是说明“目标规则”。

如果结论同时包含“应该怎样”和“现在怎样”，必须分开表述。

## 3. 权威与冲突处理

通用优先级：

1. 用户当前任务中的明确决定；
2. 当前领域的 `primary` 权威来源；
3. 当前领域的 `implementation-rule` 或 `operational` 来源；
4. 当前代码和界面，用于证明实现现状；
5. `reference` 历史/概念文档。

本项目的具体覆盖关系：

- 具体武将、装备、计策和四种羁绊数值：`游戏数据速查.md` 是唯一主数据源。
- 羁绊机制、计数、战斗副本和额外羁绊语义：`羁绊系统说明.md` 优先。
- 当前网页 Demo 的叠加、等级、经验和拖拽：`卡牌升级规则.md` 优先于宽泛设计文档。
- 当前网页的实际行为：以代码为现状证据；代码与规则不一致时标记为“实现偏差”。
- `设计文档.md` 仅用于设计背景和未定方向，不覆盖上述当前规范。
- `README.md` 用于运行方式与 Demo 范围；具体数量或行为必须与代码核对。
- 已删除的 `羁绊系统.xlsx` 不得查找、恢复或作为规则与数值依据。

冲突分三类处理：

- 权威文档与代码冲突：保留规则结论，同时报告实现偏差。
- 主规范与参考文档冲突：采用主规范，并标注参考文档已过时。
- 两个同级主规范冲突：停止作出规则决定，列出冲突并请求用户确认。

不得只依据文件修改时间解决语义冲突。

## 4. 停止检索条件

满足以下全部条件后停止继续阅读：

- 已找到当前领域的权威来源；
- 已获得回答或修改所需的具体规则；
- 已核对必要的依赖或当前实现；
- 没有未解决的同级权威冲突。

“可能还有更多资料”不是继续遍历仓库的理由。

## 5. 修改前后的约束

修改前：

- 确认要改的是规则、数据、实现还是说明；
- 检查清单中的 `depends_on` 和 `dependents`；
- 明确是否会改变权威边界。

修改后：

- 规则变化要同步检查其数据与实现依赖；
- 数据变化要检查引用该数据的说明文档；
- 新增、移动、重命名、废弃文档要更新清单和路由；
- 语义性文档变更要登记 `.harness/CHANGELOG.md`；
- 运行 `.harness/validate.ps1`。
